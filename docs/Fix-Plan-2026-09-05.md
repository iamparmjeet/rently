## 1. Purpose

This is the persistent implementation plan for the confirmed bugs, potential bugs, business-logic defects, security risks, and test gaps found in the 2026-09-05 audit.

Use this document instead of pasting the complete audit into every new chat. A new implementation chat must read:

1. `AGENTS.md`

Only one numbered slice may be implemented in one chat/branch unless this document explicitly says otherwise.

## 2. Model workflow

The intended low-cost workflow is:

1. **Luna High** implements backend, validation, tests, documentation, and tightly specified database work.
2. **Muse 1.3** implements frontend-only slices.
3. **Terra High or Sol High** reviews the design before risky work and reviews the completed diff before it is accepted.

Model responsibilities:

| Role | Model | Allowed work |
| --- | --- | --- |
| Backend implementer | Luna High | Approved, tightly scoped API/schema/test work |
| Frontend implementer | Muse 1.3 | React/UI changes using server-authoritative data |
| Test implementer | Luna High | Unit, integration, concurrency, migration, and regression tests |
| Design gate | Terra High or Sol High | Financial invariants, schema, concurrency, auth, ownership, backfill |
| Final reviewer | Terra High or Sol High | Read-only review of spec, diff, tests, migration, and rollback |

Muse 1.3 has not been independently benchmarked for this repository. It must not independently decide financial, database, authorization, billing-period, or identity semantics.

## 3. Non-negotiable rules

- Start new feature work from clean `main` (or from the active integration branch while owner-directed batching is in effect; the integration branch itself is cut from clean `main`).
- Preserve the current dirty working tree until the user explicitly resolves it.
- Create rollback tag `pre-<slice-name>` before each slice.
- Use one branch per slice. While batching, each slice merges as its own PR into the integration branch (never direct commits except CI/docs scaffolding); the integration branch merges into `main` as one rollup PR at the end.
- Use at most one migration per slice.
- Do not make `leases.agreementId` or `payments.paymentGroupId` non-null.
- Do not delete or rewrite historical ledger rows to correct balances. Use auditable reversals and allocations.
- Do not add a forever-unique positive utility-payment constraint; void-then-repay must remain possible.
- Do not point local development or tests at production Neon.
- Use a disposable local database or separate Neon branch for mutation and concurrency tests.
- Do not calculate authoritative financial balances in React.
- Do not combine opportunistic refactors with a remediation slice.
- Update `Handover.md` after every completed or interrupted slice.
- Do not commit an unverified slice.
- Do not push or deploy without user approval.

Required verification order for every implementation slice:

```bash
bun run --filter @rently/db db:generate
bun run check-types
bunx biome check <changed-files>
bun run --filter @rently/db db:migrate:test
bunx vitest run <focused-tests>
```

If a command is not applicable, record why in `Handover.md`. Financial, authorization, migration, and concurrency slices require real PostgreSQL integration tests.

## 7. Recommended review policy

- **Sol High review required:** B08, C02, C03, I02 when available.

- **Terra Medium sufficient:** ordinary server/API correctness with no new business semantics.
- **Luna High sufficient:** tests, documentation, mechanical validators, configuration, and narrowly scoped fixes after the design is approved.
- **Muse 1.3 allowed:** frontend-only implementation. Luna must run regression tests, and Terra must review any UI that presents financial totals or legal/receipt-like documents.
